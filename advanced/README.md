## Что нужно сделать?

Осталось добавить в наш интерпретатор поддержку `if`, переменных и лямбда-функций с захватом контекста.

### If

Работает как if :D Возможны 2 формы записи.

* `(if condition true-branch)`
* `(if condition true-branch false-branch)`

Сначала вычисляет `condition` и проверяет значение на истинность (см. определение истинности). Затем вычисляет либо `true-branch`, либо `false-branch` и возвращает как результат всего `if`-а.

### Переменные

Поддержка переменных реализована с помощью особых форм `define` и `set!`.

```scheme
$ (define x 1)
> ()
$ x
> 1
```

Обратите внимание на возвращаемое значение `define`. Команда `set!` используется для изменения значения **существующей**
переменной:

```scheme
$ (define x 1)
> ()
$ (set! x 2)
$ x
> 2
$ (set! y 1)
> NameError
```

Еще есть особые формы `set-car!` и `set-cdr!`. C их семантикой предлагается разобраться самостоятельно, изучив [тесты](./tests/test_pair_mut.cpp), особенно обратите внимание на тесты `SelfReferenceCar` и `SelfReferenceCdr` - разберитесь с помощью `mit-scheme`, как устроены рекурсивные структуры в Scheme.

### Лямбда-функции

Синтаксис:

* `(lambda (x) (+ 1 x))`
* `(lambda (x y) (* y x))`
* `(lambda (x) (set! x (* x 2)) (+ 1 x))`
* `(lambda () 1)`

Создаёт новую функцию. Сначала перечисляется список аргументов функции, затем её тело. Тело может состоять из нескольких выражений, в этом случае они вычисляются по порядку а результат последнего выражения становится результатом функции.

Запись `(define (fn-name <args>) <body>)` эквивалентна `(define fn-name (lambda (<args>) <body>))`. То есть, запись `(define (inc x) (+ x 1))` создаёт новую функцию `inc`.

### Захват контекста

#### Lambda capture in C++

Также возможен и захват контекста. Синтаксис примерно совпадает с C++:

```c++
auto Range(int x) {
  return [&x] () {
    ++x;
    return x;
  };
}

void F() {
  auto r = Range(10);

  std::cout << r() << std::endl; // 11
  std::cout << r() << std::endl; // 12
}
```

В **Scheme**:

```scheme
$ (define range
    (lambda (x)
      (lambda ()
        (set! x (+ x 1))
        x)))

$ (define my-range (range 10))

$ (my-range)
> 11

$ (my-range)
> 12
```

Заметьте, что такой код на С++ содержит UB - ссылка на `x` становится висящей после выхода из `Range()`. В Scheme такого не происходит - объект должен жить, пока на него кто-либо ссылается.

Вложенных scope может быть сколь угодно много. Больше примеров использования лямбда-функций вы найдете в тестах.

### Работа с памятью

В отличие от предыдущих подзадач, в этой возможен сценарий, когда два объекта ссылаются друг на друга ("циклические ссылки"). Как вы знаете, `std::shared_ptr` в таком случае не обеспечивает корректного удаления. Чтобы не делать эту подзадачу слишком сложной, в ней мы отключили на сервере детектор утечек, а вопросы правильной очистки памяти мы обсудим отдельно в [последней части](../tidy).

### Тестирование

Устроено аналогично scheme-basic. Таргет для REPL называется `scheme_advanced_repl`. Естественно, в этой подзадаче запускаются и тесты на весь предыдущий функционал.

Отключить детектор утечек локально можно, если запускать вашу программу с переменной окружения `ASAN_OPTIONS=detect_leaks=0`. Из командной строки запуск будет выглядеть так:
```bash

```
В CLion нужно поменять значение `detect_leaks` на 0 в параметрах address-санитайзера (раздел `Build, Execution, Deployment -> Dynamic Analysis Tools -> Sanitizers` настроек).

Также можно тестировать ваше решение на MacOS, используя дефолтный компилятор Apple Clang - так утечки тоже не будут ловиться.

### 0. Зачем понадобилась часть `advanced`

В `basic` уже умеем вычислять `(+ 1 2)`, но ещё не можем создать собственную переменную или функцию. Теперь нужно поддержать:

(define x 10)

Результаты отдельных строк: `()`, `15`, `()`, `100`. Важная новая идея: результат вычисления выражения зависит не только от AST, но и от окружения, в котором мы его вычисляем.

5. Тесты [`test_symbol.cpp`](tests/test_symbol.cpp), [`test_control_flow.cpp`](tests/test_control_flow.cpp), [`test_lambda.cpp`](tests/test_lambda.cpp), [`test_pair_mut.cpp`](tests/test_pair_mut.cpp).


### 1. Минимальная теория: что такое окружение и область видимости

В C++ имя `x` обычно обозначает некоторую переменную; компилятор определяет, с какой областью видимости она связана. В интерпретаторе Scheme мы должны реализовать этот механизм сами.

**Окружение (`Environment`)** — таблица соответствий `имя → Value`, у которой может быть родительское окружение. Например:

```text
Глобальное Environment
  x  → Number(10)
  +  → Native(сложение)
  ...
       ▲ parent_
       │
Локальное Environment вызова функции
  y  → Number(7)
```

Если в локальном окружении ищем `y`, находим его сразу. Если ищем `x` или `+`, переходим к родителю. Если имя отсутствует во всех окружениях, получаем `NameError`.

В C++ это отражено непосредственно в методах `Environment`:

- `Lookup(name)` — проверяет текущую `values_`, затем рекурсивно родительский `parent_`; иначе `NameError`.
- `Define(name, value)` — заносит или заменяет запись **только в текущем** `values_`.
- `Set(name, value)` — находит ближайшую существующую запись в цепочке и **изменяет её**; если не нашёл — `NameError`.

Почему важно различать `Define` и `Set`? `define` может создать новую переменную, а `set!` не имеет права молча создавать имя, которого раньше не было.

### 2. Добавить `if` — ленивое вычисление ветвей

Форма `(if condition then else)` **не** может быть обычной функцией: при обычном вызове `Eval` вычисляет *все* аргументы, включая ветку, которую надо пропустить. Поэтому `if` распознаётся в начале `Runtime::Eval`, до вычисления `unevaluated`.

Алгоритм:

1. Убедиться, что указано два либо три выражения после `if`.
2. Вычислить **только** условие: `Eval(unevaluated[0], scope)`.
3. Использовать `Truth`: только `#f` является ложью.
4. Вычислить **ровно одну** выбранную ветку; вторая должна остаться нетронутой.
5. Если условия ложное и третьего аргумента нет, вернуть пустой список (`nullptr`, вывод `()`).

```scheme
(if #t 10 missing)
(if #f missing 20)
(if 0 30 40)
```

Результаты: `10`, `20`, `30`. Имя `missing` не вызывает `NameError`, потому что соответствующая ветка не вычисляется. `0` истинно в Scheme.

Сравните с тестами [`test_control_flow.cpp`](tests/test_control_flow.cpp): там проверяется не только возвращаемое значение, но и **отсутствие побочных эффектов** пропущенной ветки.

### 3. `define` и `set!` — имена и изменяемое состояние

В одном REPL последовательно введите:

```scheme
(define x 10)
x
(set! x (+ x 5))
x
```

Результаты: `()`, `10`, `()`, `15`. Объект `Interpreter` сохраняет `global_` между вызовами `Run`, поэтому имя `x` остаётся доступным на следующей строке.

**Как исполняется `(define x 10)` в C++:**

1. В `Runtime::Eval` распознана особая форма `define`.
2. `unevaluated[0]` проверяется на `Symbol`; его имя — `x`.
3. Правая часть **вычисляется**: `Value value = Eval(unevaluated[1], scope)`.
4. `scope->Define("x", value)` записывает значение в текущую таблицу.
5. Возвращается `nullptr`, и `Print` показывает `()`.

Обратите внимание на порядок пунктов 3–4: сначала вычисляется правая часть, **потом** создаётся имя. Поэтому в пустом окружении `(define x x)` даёт `NameError`. При повторном определении `x` правая часть может обращаться к прежнему значению.

`(set! x 15)` устроен похоже, но вызывает `scope->Set`. Если написать `(set! never-defined 1)`, будет `NameError`. Важное следствие: изменяется **связь имя → значение**, а не обязательно внутренность объекта. После `(define a 1)` и `(define b a)` операция `(set! b 2)` не меняет `a`.

### 4. `lambda` — функция как обычное значение

В Scheme `lambda` — это **выражение создания функции**, а не момент выполнения её тела:

```scheme
(lambda (x) (+ x 1))
((lambda (x) (+ x 1)) 5)
```

Первое выражение возвращает объект процедуры (в данном проекте печатается как `#<procedure>`); второе **создаёт и сразу вызывает** функцию, результат `6`.

C++-класс `Closure` в [`common/interpreter_engine.h`](../common/interpreter_engine.h) хранит:

```text
Closure
 ├── args_: имена параметров, например ["x", "y"]
 ├── body_: AST выражений тела, например [(+ x y)]
 └── scope_: окружение, в котором lambda была СОЗДАНА
```

Ветка `lambda` в `Runtime::Eval` не вызывает `Eval` на теле: она собирает список параметров через `Parameters`, берёт оставшиеся AST-узлы и создаёт `Make<Closure>(..., scope)`. `Parameters` проверяет, что параметры являются символами и не повторяются.

#### Как вызывается пользовательская функция

Рассмотрим `((lambda (x) (+ x 1)) 5)`.

```text
1. Eval головы (lambda ...) → Closure{params=[x], body=[(+ x 1)], scope=global}
2. Eval аргумента 5 → Number(5)
3. Создать call_scope = Environment(parent=closure->Scope())
4. call_scope.Define("x", Number(5))
5. Eval((+ x 1), call_scope) → Number(6)
6. Вернуть 6 и напечатать "6"
```

Это можно найти в `Eval` после обычной ветки `if (auto native = As<Native>(proc))`: обработчик `if (auto closure = As<Closure>(proc))` проверяет число аргументов, создаёт окружение вызова, связывает параметры с аргументами и последовательно вычисляет выражения `closure->Body()`. Результат **последнего выражения** становится результатом вызова. Поэтому допустимо тело из нескольких выражений:

```scheme
((lambda (x) (set! x (* x 2)) (+ x 1)) 20)
```

Ответ `41`: сначала `x` меняется с `20` на `40`, затем вычисляется `(+ x 1)`.

#### Синтаксический сахар `define` для функций

```scheme
(define (square x) (* x x))
```

Эквивалентен по смыслу:

```scheme
(define square (lambda (x) (* x x)))
```

В реализации это **отдельная ветка `define`**, где первый аргумент является `Cell`: её `first_` — имя функции, а `second_` — параметры. Строится `Closure`, а затем сразу записывается в текущий `Environment`.

### 5. Лексическая область видимости — почему функция не берёт «ближайший x»

В Scheme используется **лексическая (статическая) область видимости**: свободное имя в теле функции ищется в окружении, где функция **была создана**, а не в окружении, из которого её вызвали.

Выполните последовательно:

```scheme
(define x 100)
(define get-x (lambda () x))
((lambda (x) (get-x)) 1)
```

Результат последней строки — **`100`, а не `1`**. Почему?

```text
Глобальное окружение: x = 100; get-x → Closure
                      ▲
                      │ scope_ у get-x

Окружение внешнего вызова: x = 1
        │
        └─ вызываем get-x, но его parent берётся из get-x.scope_,
           то есть из ГЛОБАЛЬНОГО окружения, а не отсюда.
```

В коде решающая строчка:

```cpp
auto call_scope = Make<Environment>(closure->Scope());
```

Если бы вместо `closure->Scope()` был передан текущий `scope` вызывающего выражения, мы получили бы **динамическую область видимости** и результат `1`. Это другой язык и неправильная реализация Scheme.

### 6. Замыкание — код + сохранённое окружение

Теперь самая важная часть `advanced`. **Замыкание** (*closure*) — функция, которая сохраняет доступ к внешним переменным даже после завершения внешней функции. За счёт `std::shared_ptr<Environment>` её окружение не уничтожается слишком рано.

Для примера возьмём счётчик:

```scheme
(define make-counter
  (lambda (x)
    (lambda ()
      (set! x (+ x 1))
      x)))
(define counter (make-counter 10))
(counter)
(counter)
```

В тестах эти определения отправляются интерпретатору по одному; **наш REPL принимает по одному выражению на строку**, поэтому при ручном вводе запишите каждое `define` целиком на одной строке:

```scheme
(define make-counter (lambda (x) (lambda () (set! x (+ x 1)) x)))
(define counter (make-counter 10))
(counter)
(counter)
```

Результаты: `()`, `()`, `11`, `12`. Пошагово:

1. `make-counter` — глобальная функция с одним параметром `x`.
2. При `(make-counter 10)` создаётся **временное окружение E** с `x = 10`, родитель которого — глобальное окружение.
3. В теле создаётся **внутренний `Closure`** с `scope_ = E`. Он возвращается как значение и записывается в глобальную переменную `counter`.
4. Внешний вызов завершается, но E не исчезает: его по-прежнему удерживает `counter → Closure → E`.
5. При `(counter)` создаётся новое окружение вызова с родителем E. `Set("x", ...)` не находит `x` в новом окружении и изменяет **ту же запись** в E: `10 → 11`.
6. Второй вызов снова получает доступ к E и меняет `11 → 12`.

```text
Глобальное окружение
  make-counter ──► Closure внешней функции
  counter ───────► Closure внутренней функции
                         │ scope_
                         ▼
                   E: { x = 10 }  ──► parent: глобальное
                         ▲
           1-й вызов: x = 11
           2-й вызов: x = 12
```

**Не путайте:** `Closure::scope_` — окружение **создания**, а `call_scope` — **новое окружение каждого вызова**. Хранилище переменной `x` находится в захваченном E. Это объясняет, почему счётчик не обнуляется при каждом вызове.

Дополнительный опыт: создать два счётчика из `make-counter` с разными начальными значениями — их окружения будут независимыми. Посмотрите тесты `LambdaClosure`, `LambdasShareContext` в [`tests/test_lambda.cpp`](tests/test_lambda.cpp): несколько замыканий могут, напротив, **совместно владеть одним окружением**.

### 7. рекурсия и переопределение функций

Замыкания позволяют писать рекурсивные функции:

```scheme
(define (fact n) (if (= n 0) 1 (* n (fact (- n 1)))))
(fact 5)
```

Ответ `120`. Возникает вопрос: в момент создания `Closure` переменной `fact` в глобальной таблице ещё нет. Почему рекурсия работает?

**Потому что `Closure` хранит указатель на само окружение, а не его копию на момент создания.** Сначала создаётся `Closure` со ссылкой на `global_`, затем `Define` записывает `fact` в `global_`. Когда тело выполняется позднее, поиск `fact` в том же окружении уже успешен. Именно поэтому важна ссылочная семантика окружений.

Аналогично возможно переопределить встроенную функцию, сохранив оригинал:

```scheme
(define add +)
(define (+ x) (add x 1))
(+ 5)
```

Результат последней строки — `6`. `add` и новый `+` — **значения-процедуры**, которые лежат в таблице имён. Посмотрите тест `Redefinition`.

### 8. `set-car!`, `set-cdr!` и разделяемые объекты

В `basic` мы могли читать пары через `car` и `cdr`. В `advanced` допускается их **изменять на месте**:

- `(set-car! pair expression)` — заменить `first_` уже существующей `Cell`.
- `(set-cdr! pair expression)` — заменить `second_` у этой же `Cell`.

Например:

```scheme
(define xs '(1 2 3))
(define ys xs)
(set-car! xs 99)
(car ys)
```

Последнее выражение возвращает `99`, потому что `xs` и `ys` указывают на **один и тот же объект `Cell`**. Это не то же самое, что `(set! ys ...)`: здесь мы изменили содержимое объекта, а не запись в таблице `Environment`.

Побочный эффект: можно сделать циклический список:

```scheme
(define p '(1 . 2))
(set-cdr! p p)
(car (cdr (cdr p)))
```

Результат `1`, потому что хвост `p` указывает на `p` же. **Не пытайтесь вывести значение `p` целиком**: циклическую структуру невозможно напечатать обычной конечной записью списка. В этой реализации `Print` обнаруживает цикл и бросает `RuntimeError`.

При циклах обнаруживается и более глубокая проблема: пара, которая держит себя через `std::shared_ptr`, никогда не освободится только подсчётом ссылок. Поэтому пятая часть `tidy` вводит сборку мусора. Аналогичные циклы возможны между `Environment` и `Closure`.

### 9. Ошибки, которые могут быть незаметны при поверхностном тестировании

| Выражение | Поведение | Что проверяется |
| --- | --- | --- |
| `(if #f missing 7)` | `7` | Невыбранная ветка не вычисляется |
| `(if)` | `SyntaxError` | Арность особой формы |
| `(set! unknown 3)` | `NameError` | `set!` не создаёт имя |
| `(lambda (x x) x)` | `SyntaxError` | Дублирующиеся параметры |
| `((lambda (x) x) 1 2)` | `RuntimeError` | Количество переданных аргументов |
| `(car 10)` | `RuntimeError` | Проверка типов |

Тесты на `advanced` включают **все прежние** проверки из `tokenizer`, `parser`, `basic`. Иными словами, добавление нового поведения не должно ломать прежнее.

### 10. Практическая проверка и отладка

Из **корня `scheme/`**:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target scheme_advanced_repl test_scheme_advanced_local -j 4
ctest --test-dir build -R '^test_advanced$' --output-on-failure
./build/scheme_advanced_repl
```

Для проверки пошагового вычисления в отладчике поставьте breakpoint на `Runtime::Eval` и проследите три места: `scope->Lookup` при чтении символа, `scope->Define` при объявлении, `call_scope = Make<Environment>(closure->Scope())` при вызове лямбды. На каждом шаге задавайте вопрос: **какой объект `Environment` передан сюда и где находится искомое имя?**

**Два задания с ответами для самопроверки:**

1. Выполните `(define x 100)`, `(define f (lambda (x) (lambda () x)))`, `(define g (f 7))`, `(g)`. Ответ: `7`, потому что внутренняя функция захватила окружение вызова `f` со своим `x = 7`.
2. Выполните `(define x 100)`, `(define g (lambda () x))`, `((lambda (x) (g)) 7)`. Ответ: `100`, потому что `g` ищет `x` в окружении **создания**, а не в окружении вызывающей её функции.
