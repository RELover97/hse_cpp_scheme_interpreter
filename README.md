В этом задании вам предстоит реализовать интерпретатор для LISP-подобного языка программирования, а именно некоторого подмножества Scheme. 

Язык будет состоять из:
 - Примитивных типов: целых чисел, bool-ов и _символов_ (идентификаторов).
 - Составных типов: пар и списков.
 - Переменных с синтаксической областью видимости.
 - Функций и лямбда-выражений.

Ваша программа должна будет выполнять выражения языка и возвращать результат выполнения.

```
    1 => 1
    (+ 1 2) => 3
```
Обозначение `=>` в примерах здесь и далее разделяет выражение и результат его выполнения.

## Выполнение выражений
Выполнение языка происходит в 3 этапа:

**Токенизация** - преобразует текст программы в последовательность атомарных лексем. 

**Синтаксический анализ** - преобразует последовательность токенов в [AST](https://en.wikipedia.org/wiki/Abstract_syntax_tree).  AST в LISP-подобных языках программирования представляется в виде списков. 
   
**Вычисление** - рекурсивно обходит AST программы и преобразует его в соответствии с набором правил.

### Пример

Выражение 
```
    (+ 2 (/ -3 +4))
``` 
в результате токенизации превратится в список токенов:
```
    { 
        OpenParen(),
        Symbol("+"),
        Number(2),
        OpenParen(),
        Symbol("/"),
        Number(-3),
        Number(4),
        CloseParen(),
        CloseParen()
    }
```
     
 Последовательность токенов в результате синтаксического анализа
 превратится в дерево:
     
```
    Cell{
        Symbol("+"),
        Cell{
            Number(2),
            Cell{
                Cell{
                    Symbol("/"),
                    Cell{
                        Number(-3),
                        Cell{
                            Number(4),
                            nullptr
                        }
                    }
                }
                nullptr
            }
        }
    }
```
Результатом же выполнения выражения будет 

```
    (+ 2 (/ -3 +4)) => 1
```

## Краткая теория


### 1. Что такое Scheme и чем он отличается от C++?

**Scheme** — небольшой язык из семейства Lisp. В этом проекте мы реализуем **подмножество** языка, а не всю стандартную спецификацию. Главное внешнее отличие — *префиксная запись*: в большинстве вызовов сначала записывается операция (или функция), затем её аргументы.

| Идея | Привычная запись | Scheme | Результат |
|---|---|---|---|
| Сложить два числа | `2 + 3` | `(+ 2 3)` | `5` |
| Умножить сумму | `(2 + 3) * 4` | `(* (+ 2 3) 4)` | `20` |
| Вызвать функцию | `square(5)` | `(square 5)` | зависит от `square` |
| Условие | `x > 0 ? 1 : 0` | `(if (> x 0) 1 0)` | зависит от `x` |

Скобки в Scheme — не просто оформление и не «команды по порядку»: они задают вложенную структуру. Например, `(+ 2 (* 3 4))` — **один** вызов `+` с двумя аргументами: `2` и результатом вызова `*`. Он даёт `14`. Внешнее `+` не начинает складывать числа, пока внутреннее `*` не вычислено.

**Словарь из пяти сущностей** (этого хватит на семинар):

- **Число** (`42`, `-7`) — литерал, при вычислении остаётся самим собой.
- **Символ** (`x`, `+`, `square`) — имя, которое вычислитель может найти в окружении. Поэтому `+` — *не отдельный лексический оператор*, а имя функции.
- **Булево значение** (`#t`, `#f`) — истина и ложь; в нашем языке только `#f` считается ложным.
- **Пара** `(a . b)` — структура из **двух полей**, `first` и `second` (в Scheme их традиционно называют `car` и `cdr`).
- **Список** `(1 2 3)` — последовательность связанных пар, заканчивающаяся пустым списком `()`. Пустой список — не то же самое, что `#f`.

**Пример определения и вызова функции** (этап `advanced`):

```scheme
(define (square x) (* x x))
(square 5) ; результат 25
```

Точку с запятой здесь использовали только в примере записи Scheme: она начинает комментарий до конца строки. В нашем учебном интерпретаторе поддерживается ограниченный синтаксис.

### 2. Что такое интерпретатор и какие задачи у трёх стадий?

**Интерпретатор** — программа, которая читает текст другой программы и выполняет описанные в нём действия.

```text
Ввод пользователя:       (+ 2 (* 3 4))
                                  │
                                  ▼
1. Tokenizer (лексика):   (, +, 2, (, *, 3, 4, ), )
   «Какие здесь слова, числа и скобки?»
                                  │
                                  ▼
2. Parser (синтаксис):   дерево «вызов +»
                           ├── Number(2)
                           └── «вызов *»
                               ├── Number(3)
                               └── Number(4)
   «Как токены сгруппированы?»
                                  │
                                  ▼
3. Eval (семантика):     *: 3 × 4 → 12; +: 2 + 12 → 14
   «Что выражение означает и каково его значение?»
                                  │
                                  ▼
4. Print:                "14"
```

Такое разделение принципиально: токенизатор не отслеживает вложенность скобок, парсер не выполняет арифметику, вычислитель не читает символы из потока. Благодаря этому каждый этап можно тестировать отдельно.

### 3. AST: зачем нужно абстрактное синтаксическое дерево?

Возьмём два текста: `(+ 2 3)` и `(+ 2 (* 3 4))`. Оба содержат числа и символы, но у них разная вложенность, а значит, и разный способ вычисления. Плоский список токенов отражает порядок чтения; **AST** (*Abstract Syntax Tree*) отражает структуру выражения и связи между его частями.

Условное, удобное для человека изображение AST:

```text
                    вызов (+)
                    /      \
                   2      вызов (*)
                           /    \
                          3      4
```

Это схематическое дерево вызовов. Реальная модель этого проекта устроена чуть иначе: парсер хранит списки как цепочки объектов `Cell`. У каждой `Cell` две ссылки:

```cpp
class Cell : public Object {
    Value first_;   // текущий элемент списка
    Value second_;  // оставшаяся часть списка (или хвост пары)
};
```

Для `(1 2 3)` структура выглядит так:

```text
           Cell ────────► Cell ────────► Cell ────────► nullptr
           │first        │first        │first           ()
           ▼             ▼             ▼
           1             2             3
```

То есть `(1 2 3)` — сокращение для `(1 . (2 . (3 . ())))`. В нашем C++ пустой список `()` представляется `nullptr`, а не `Number(0)` и не `Boolean(false)`.

Есть и неправильные списки (improper lists): `(1 2 . 3)` отличается от `(1 2 3)` последним хвостом:

```text
обычный:     Cell(1, Cell(2, Cell(3, nullptr)))
с точкой:    Cell(1, Cell(2, Number(3)))
```

Самая важная мысль для чтения `parser.cpp`: парсер собирает структуру, не выясняя, допустима ли такая функция и что она вычислит. Например, `(foo 2)` синтаксически корректно; ошибка неизвестного имени `foo` возникает позднее, на этапе вычисления.

### 4. Как алгоритм строит AST: рекурсивный спуск

**Рекурсивный спуск** — способ написать парсер, в котором функции повторяют вложенную структуру грамматики. Нам нужны две операции:

- `Read` читает одно выражение: число, имя, вложенный список или `'` перед выражением.

- `ReadList` читает содержимое между `(` и `)`, многократно вызывая `Read`. Если очередной элемент сам начинается с `(`, происходит рекурсивный вызов.

Разбор `(+ 2 (* 3 4))` по шагам:

```text
Read видит '(' → ReadList внешнего вызова
   Read видит '+' → Symbol("+")
   Read видит '2' → Number(2)
   Read видит '(' → ReadList внутреннего вызова
      Read видит '*' → Symbol("*")
      Read видит '3' → Number(3)
      Read видит '4' → Number(4)
      видим ')' → внутренний список готов
   видим ')' → внешний список готов
```

Почему `std::shared_ptr<Object>`? У AST разные виды узлов (`Number`, `Symbol`, `Cell`), поэтому нужен общий базовый `Object`. Парсер возвращает владение получившимся объектом через `Value = std::shared_ptr<Object>`: дерево может прожить дольше вызова `Read`. Это не означает, что `shared_ptr` сам решит проблему циклов — об этом в разделе `tidy`.

### 5. Что предстоит после AST: вычисление, окружения и сборка мусора

В `basic` интерпретатор вычисляет дерево: для `(+ 2 (* 3 4))` сначала вычисляется `(* 3 4)` до `12`, затем `( + 2 12 )` до `14` (пробелы здесь только для наглядности). Формы `quote`, `if`, `and`, `or` требуют особого порядка вычисления аргументов: например, `'(+ 2 3)` возвращает список как данные, а не число `5`.

В `advanced` появляется **окружение** — таблица имён и значений (`x → 10`), связанная с родительским окружением. **Замыкание** хранит параметры, тело функции и ссылку на окружение **создания**:

```text
global: make-counter ──► Closure
                          │
                        вызов (make-counter 10)
                          ▼
                    local: x = 10 ◄──── захвачено внутренней lambda
                          │
                       (counter) → x = 11 → возвращает 11
                       (counter) → x = 12 → возвращает 12
```

В `tidy` разбираем проблему памяти: `shared_ptr` освобождает объект при обнулении счётчика ссылок, но не разрывает циклы. Например, `Environment → Closure → Environment`. Сборщик мусора идёт от глобального окружения, отмечает достижимые объекты и очищает ссылки в недостижимых циклах (*mark-and-sweep*).

### Часть I. Токенизатор: из текста в последовательность токенов

#### 3. Что именно требуется

Сначала реализуем класс `Tokenizer`, который читает один токен из потока, хранит его как текущий и сдвигается на следующий по вызову `Next()`.

В нашем подмножестве Scheme предусмотрены:

- Числа, например `42`, `-7`, `+18`.
- Символы-идентификаторы, например `foo`, `number?`, `+`, `-`, `>=`.
- Скобки `(` и `)`, апостроф `'` и точка `.`.
- Булевы литералы `#t` и `#f` (лексически это символы; при разборе они превращаются в `Boolean`).

Важно: токен `Symbol("+")` отличается от числа `Constant(+7)`. В выражении `3+4` нет необходимости в пробелах: получатся три токена `3`, `+`, `4`.

#### Шаг 3.1. Представим альтернативы через `std::variant`

Откройте [tokenizer/tokenizer.h](tokenizer/tokenizer.h):

```cpp
struct SymbolToken { std::string name; /* ... */ };
struct ConstantToken { int64_t value; /* ... */ };
struct QuoteToken { /* ... */ };
struct DotToken { /* ... */ };
enum class BracketToken { OPEN, CLOSE };

using Token = std::variant<ConstantToken, BracketToken,
                           SymbolToken,А QuoteToken, DotToken>;
```

Почему не набор полей `is_number`, `is_symbol`, `is_dot`? В таком наборе возможно нелепое сочетание двух `true`, а с `std::variant` активен ровно один вариант. Это пример выражения инварианта программы через систему типов.

`std::get_if<ConstantToken>(&token)` возвращает указатель на число или `nullptr` (см. `common/parser_impl.h`). 

`std::visit` позволяет обработать любой вариант. Посмотрите пример печати в [standalone/show_tokens.cpp](standalone/show_tokens.cpp).

### Шаг 3.2. Сформулируем инвариант `Tokenizer`

Откройте `Tokenizer` в [tokenizer/tokenizer.h](tokenizer/tokenizer.h):

- Сразу после конструктора текущий токен уже прочитан, если поток не пуст.
- `IsEnd()` отвечает, есть ли вообще текущий токен.
- `GetToken()` возвращает его **без продвижения**.
- `Next()` потребляет символы до следующего токена или конца потока.

Поэтому безопасен следующий сценарий:

```cpp
std::istringstream input("12 + 3");
Tokenizer tokens(&input);
// GetToken(): Constant(12)
// GetToken(): снова Constant(12)
tokens.Next();
// GetToken(): Symbol(+)
```

`token_` имеет значение по умолчанию только для инициализации `std::variant`; когда `end_ == true`, обращаться к нему нельзя. Программно мы запрещаем это через `SyntaxError`.

### Шаг 3.3. Правильно читаем `std::istream`

Разберите файл [common/tokenizer_impl.h](common/tokenizer_impl.h), функции `Tokenizer::Tokenizer`, `Tokenizer::Next` и `Tokenizer::GetToken`.

Первый цикл `Next()` пропускает пробельные символы через `peek()` и `get()`:

```cpp
while (in_->peek() != EOF &&
       std::isspace(static_cast<unsigned char>(in_->peek()))) {
    in_->get();
}
```

`peek()` **смотрит** на следующий символ, но не извлекает его. `get()` **потребляет** символ. Это существенно: если на границе двух токенов мы прочитали первый символ следующего, получим ошибку или будем вынуждены применять `putback()`.

Методы возвращают `int`, потому что `EOF` не обязан помещаться в `char`. Преобразование к `unsigned char` перед `std::isspace`/`std::isdigit` необходимо для корректного использования функций `<cctype>`.

Далее `Next()` распознаёт в первую очередь односимвольные токены: скобки, апостроф, точку. Для цифры или знака с последующей цифрой собирается строка числа. Для буквенного начала собирается строка символа; набор допустимых символов выделен в `SymbolStart` и `SymbolContinue`.

Граничный случай: знак `-` перед цифрой — часть числа, а в одиночку — имя функции вычитания. Поэтому обработка знака отделена от обычных символов. Переполнение числа при `std::stoll` преобразуется в `SyntaxError`, а не отдаётся вызывающей стороне как `std::out_of_range`.

### Шаг 3.4. Проверяем реализацию

```bash

./build/scheme_show_tokens '-2 - 2'
ctest --test-dir build -R '^test_tokenizer$' --output-on-failure
```

В первой команде двойные кавычки оболочки позволяют включить апостроф в исходное выражение как обычный символ.

Ожидаем в первом случае: `Constant(4)`, `Symbol(+)`, `CloseParen`, `Quote`, `Dot`. Во втором: `Constant(-2)`, `Symbol(-)`, `Constant(2)`.

Не пытайтесь разбирать скобки внутри токенизатора. Он должен вернуть `OpenParen`/`CloseParen` даже для бессмысленной последовательности `))(`. Проверка согласованности скобок — задача парсера.

## Часть II. Парсер: из последовательности токенов в AST

### 4. Почему одного списка токенов недостаточно

В выражении `(+ 2 (* 3 4))` внешнее сложение получает два аргумента: число 2 и вложенное выражение умножения. Плоская последовательность токенов не показывает непосредственно границы этих аргументов — дерево показывает.

Преобразуем `(1 2 3)` в цепочку пар:

```text
              Cell
             /    \
            1      Cell
                  /    \
                 2      Cell
                       /    \
                      3      nil
```

`Cell(first, second)` — пара из двух объектов; конец правильного списка — `nullptr`. Запись `(1 2 . 3)` почти такая же, но в последнем `second` хранится `Number(3)`, а не ещё один `Cell` или `nullptr`.

### Шаг 4.1. Создаём иерархию объектов

Откройте [common/object_model.h](common/object_model.h):

- `Object` — базовый полиморфный тип, имеющий виртуальный деструктор.
- `Number` хранит `int64_t`.
- `Symbol` хранит имя.
- `Boolean` хранит логическое значение.
- `Cell` содержит `Value first_` и `Value second_`.
- `using Value = std::shared_ptr<Object>` — указатель на произвольный объект дерева.

Почему `std::shared_ptr`, а не `std::unique_ptr`? Значения списков могут в дальнейшем разделяться между несколькими выражениями и переменными. Для базового AST `unique_ptr` тоже мог бы работать, но усложнил бы последующий переход к разделяемым значениям Scheme.

Функции `As<T>` и `Is<T>` внизу файла используют `std::dynamic_pointer_cast<T>`: так можно безопасно проверить вид узла, не выполняя ошибочное преобразование указателя.

Тонкость: `nullptr` здесь обозначает сам объект пустого списка `()`. При разборе `(())` будет существовать внешняя `Cell`, у которой оба поля равны `nullptr`. Это не равнозначно полному отсутствию выражения.

### Шаг 4.2. Выводим рекурсивный алгоритм

Откройте [common/parser_impl.h](common/parser_impl.h). Работу делят две функции:

1. `Read(tokens)` читает одно произвольное выражение.
2. `ReadList(tokens)` читает содержимое списка до закрывающей скобки.

В `Read` проверяем текущий токен:

```text
Число   →  Number
Имя     →  Symbol
#t/#f   →  Boolean
'       →  прочитать следующее выражение и обернуть в (quote ...)
(       →  ReadList
) или . →  SyntaxError
```

Важный инвариант: `Read` читает ровно одно выражение и оставляет токенизатор на первом токене после него. Благодаря этому вызывающий код может последовательно читать несколько выражений из общего потока.

При `(` перед вызовом `ReadList` открывающая скобка уже потреблена. Иначе мы бы разобрали её второй раз или получили бесконечную рекурсию.

### Шаг 4.3. Собираем список с конца

В `ReadList` мы добавляем распарсенные элементы во временный `std::vector<Value>`, пока не увидим `)`. Затем сворачиваем последовательность справа налево:

```cpp
Value list;
for (auto it = elements.rbegin(); it != elements.rend(); ++it) {
    list = std::make_shared<Cell>(*it, list);
}
```

Для `[1, 2, 3]` состояния будут такими:

```text
list = nil
list = Cell(3, nil)
list = Cell(2, Cell(3, nil))
list = Cell(1, Cell(2, Cell(3, nil)))
```

Почему не наоборот? При добавлении в начало списка слева направо мы бы получили `(3 2 1)`.

Для записи `(1 2 . 3)` алгоритм тот же, но значение `list` изначально равно `Number(3)`, прочитанному после точки. Перед точкой должен быть хотя бы один элемент; после хвоста должна идти ровно одна закрывающая скобка.

### Шаг 4.4. Цитирование — синтаксический сахар

В Scheme запись `'x` обозначает `(quote x)`, а `'(1 2)` обозначает `(quote (1 2))`. Она позволяет указать интерпретатору: не вычисляй выражение, а воспринимай его как данные. Парсер в `Read` превращает апостроф в обычное дерево:

```cpp
Value quoted = Read(tokens);
return std::make_shared<Cell>(std::make_shared<Symbol>("quote"),
           std::make_shared<Cell>(quoted, nullptr));
```

Это архитектурно полезно: вычислитель дальше знает только форму `quote` и не должен специально обрабатывать токен `'`.

### Шаг 4.5. Разбираем ошибочные программы

Вместо падения или неопределённого поведения парсер бросает `SyntaxError` для:

```text
(         — не закрыт список
(1 .)    — отсутствует хвост пары
(. 2)    — нет элемента слева от точки
(1 . 2 3) — после хвоста стоит лишний элемент
)         — закрывающая скобка без открывающей
'         — после апострофа нет выражения
```

Эти проверки находятся в `Read` и `ReadList`; обратите внимание, где именно токенизатор переводится на следующий токен. Функция `Read` не обязана требовать конец всего потока — эту проверку делает верхний уровень `Interpreter::Run`.

### Шаг 4.6. Проверяем построенное дерево

```bash
./build/scheme_show_ast '(1 2 . 3)'
./build/scheme_show_ast '(+ 2 (* 3 4))'
ctest --test-dir build -R '^test_parser$' --output-on-failure
```

Для `(1 2 . 3)` вы увидите:

```text
Cell
  Number 1
  Cell
    Number 2
    Number 3
```

Для сравнения попробуйте `(1 2 3)`: последним дочерним узлом станет ещё одна `Cell` с `Number 3` и `nil`.

## Часть III. Вычисление

### 5. Часть 3 — `basic`: от AST к результату


В первых двух частях мы превратили исходный текст в дерево, но не выполняли его. В третьей части появляется вычислитель `Eval`. Он принимает объект AST (`Value`) вместе с окружением и возвращает другой объект (`Value`). Текстовая строка появляется только на последнем шаге, в `Print`.

```text
(+ 2 (* 3 4))
   │
   ├─ AST для +, 2, (* 3 4)
   │        │ Eval
   │        ▼
   ├─ Eval(*) → Native, 3 и 4 → числа → Number(12)
   ├─ Eval(+) → Native, 2 и 12 → числа → Number(14)
   │        │ Print
   ▼        ▼
  "14"
```

**Три категории выражений:**

- **Число и `Boolean`** вычисляются в самих себя: `7 → 7`, `#t → #t`.

- **Символ** — это имя: `+` разрешается в объект встроенной процедуры `Native`, а `unknown` приводит к `NameError`.

- **Список, стоящий в позиции выражения**, обычно означает **вызов**: сначала вычисляется его первый элемент как процедура, потом аргументы, затем вызывается процедура. Поэтому `(1 2)` — ошибка, а не список данных.

Откройте [`basic/scheme.cpp`](basic/scheme.cpp), затем [`common/object_model.h`](common/object_model.h) и [`common/interpreter_engine.h`](common/interpreter_engine.h):

1. `Runtime::Run`: `Tokenizer → Read → Eval → Print`.
2. `Runtime::Eval`: правила вычисления атома, символа и вызова.
3. `Runtime::InstallBuiltins`: регистрация `Native`-объектов с помощью `bind`; найдите реализацию `+`.
4. `Runtime::Truth`: в Scheme **только `#f` ложно**; `0` и пустой список-значение истинны.
5. `Runtime::Print`: превращает объект результата в строку, в том числе пары `(1 . 2)`.

### Почему существуют особые формы

Для обычных функций все аргументы вычисляются заранее. Но `(quote (+ 1 2))` должен возвращать список `(+ 1 2)`, не вычисляя сложение; `(and #f unknown)` должен вернуть `#f`, не обращаясь к `unknown`. Поэтому `quote`, `and`, `or` проверяются до общего вычисления аргументов. `and` и `or` могут возвращать не только boolean: `(and 1 2 3) → 3`.

**Списки:** `Cell` содержит `first_` и `second_`. `(list 1 2 3)` — цепочка из трёх `Cell`, заканчивающаяся `nullptr`. Пара `(cons 1 2)` печатается `(1 . 2)`: её хвост — число, а не список. В `InstallBuiltins` найдите `cons`, `car`, `cdr`, `list`, `list-ref` и `list-tail`.

После этой схемы переходите к разделам **1–9** [`basic/README.md`](basic/README.md): там приведены разбивка `Eval` по строкам, таблицы операций, выводы тестов, проверка ошибок и рекомендации для демонстрации.

## 6. Часть 4 — `advanced`: имена, функции и замыкания

### Что изменяется по сравнению с `basic`

Теперь один и тот же символ может иметь разные значения в разных областях видимости. Поэтому вычислитель работает с `Environment`: словарём `имя → Value`, у которого есть ссылка `parent_` на внешнюю область.

```text
global:    x = 100, + = Native(...)
                  ▲
                  │ parent_
local:     x = 5, y = 7
```

`Lookup("x")` в `local` найдёт локальное `5`, а `Lookup("+")` перейдёт в `global`. `Define` добавляет запись **в текущую таблицу**; `Set` меняет **ближайшую существующую запись** и бросает `NameError`, если не находит её.

### Как добавить язык шаг за шагом

1. `if`: вычисляет условие и только выбранную ветку; например, `(if #t 1 unknown) → 1`.

2. `define` и `set!`: создают и меняют имена. `(define x 10)`, `(set! x 11)`, затем `x → 11`. Операции выполняются в одном экземпляре `Interpreter`, сохраняющем глобальное окружение между вызовами `Run`.

3. `lambda`: создаёт объект `Closure`, содержащий параметры, AST тела и окружение создания. Само тело в момент создания не выполняется.

4. Вызов `Closure`: `Eval` создаёт дочернее окружение с родителем `closure->Scope()`, связывает параметры с готовыми аргументами и выполняет выражения тела по порядку.

5. Захват переменных и рекурсия: возвращённая лямбда удерживает окружение создания. Поэтому счётчик может помнить и изменять своё `x` между вызовами.

6. `set-car!` и `set-cdr!`: меняют объект пары на месте, из-за чего возможны циклы ссылок — тема пятой части `tidy`.

### Пример

```scheme
(define make-counter (lambda (x) (lambda () (set! x (+ x 1)) x)))
(define counter (make-counter 10))
(counter)
(counter)
```

Результаты по строкам: `()`, `()`, `11`, `12`. После `(make-counter 10)` локальное окружение с `x = 10` не исчезает: на него ссылается `Closure` в переменной `counter`. Каждый новый вызов получает своё временное окружение, но ищет и изменяет **один и тот же захваченный `x`**.

В [`common/interpreter_engine.h`](common/interpreter_engine.h) нужно показать `Environment::{Lookup, Define, Set}`, `Closure::{Params, Body, Scope}` и создание `call_scope` внутри `Runtime::Eval`. Подробная трассировка, пример лексической (а не динамической) области видимости, рекурсия, мутация пар и тесты разобраны в [`advanced/README.md`](advanced/README.md).


## 7. `tidy`: почему `std::shared_ptr` недостаточно


Рассмотрите пример:

```scheme
(define x '(1 . 2))
(set-cdr! x x)
```

Второй оператор создаёт цикл: поле `second_` пары указывает на ту же пару. Если хранить объекты только в `shared_ptr`, счётчик ссылок никогда не станет нулём, даже если `x` больше не доступен из программы. Второй источник циклов — окружение, которое содержит замыкание, а замыкание ссылается на своё окружение.

В исходной постановке предлагается собственный `Heap` с mark-and-sweep. В нашем коде реализован эквивалентный по цели вариант: `GarbageCollector` отслеживает все созданные управляемые объекты через `weak_ptr`, а `Trace` и `DropReferences` описывают граф ссылок. Он не меняет язык или интерфейс `Interpreter`.

Алгоритм `GarbageCollector::Collect`:

1. Начинаем от корня: глобального `Environment`, который должен пережить вызовы `Run`.

2. Обходим рёбра ссылок (`Environment -> Value`, `Closure -> Environment/AST`, `Cell -> first/second`) и помечаем достижимые узлы.

3. У всех недостижимых узлов очищаем сильные ссылки (`DropReferences`). Это разрывает циклы и освобождает память обычными деструкторами C++.

4. Удаляем из реестра устаревшие `weak_ptr`.

Сборка мусора вызывается после каждого `Run`, а не только в деструкторе интерпретатора. В последнем случае длинный интерактивный сеанс мог бы удерживать неограниченное число мёртвых циклических структур.

Почему нельзя просто заменить все `shared_ptr` на `weak_ptr`? Потому что объекты, на которые никто не владеет через сильную ссылку, исчезнут раньше времени; например, возвращённое замыкание потеряет своё локальное окружение. `weak_ptr` хорош для реестра наблюдения, но не заменяет анализ достижимости в общем случае.

В локальных тестах `tidy` установлен счётчик обычных `new` и `delete` из [standalone/allocations_checker.cpp](standalone/allocations_checker.cpp). Он проверяет локальные тесты, но не полностью повторяет инструментирование внешнего курса. Для воспроизведения всех проверок на выделения/освобождения в среде курса используйте её оригинальный `allocations_checker`.
